# prod-observability

**로그가 진실의 창이다.** 테스트가 통과한 것과 프로덕션에서 도는 것은 다르다 — 보고할 때 둘을 갈라 말한다.

## 어디서 읽나

- Railway 프로젝트 `아이기론`(`3ef2b6c7-2674-43d5-80c6-dd6be297ed04`), 서비스 `epiweather-api`(`bf7384d4-2ae6-41b6-ab28-754bcf01346d`).
  같은 계정의 `neo-oceanos` 프로젝트와 `MALAKH` 서비스는 **무관하다.**
- 샌드박스는 `railway.app`/`backboard.railway.com` 에 curl 이 막힌다(프록시 403 — 정책이지 장애가 아니다). **Railway MCP** 로 읽는다:
  `list-deployments`(최신 배포·시각·커밋) → `get-logs(deploymentId=…, filter="…", startDate/endDate)`.
- `master` push 는 자동 배포된다. 머지 직후 배포가 시작돼 약 1분 안에 `SUCCESS` 가 된다(#47: 09:26:05 시작 → 09:26:39).
  `meta.commitHash` 가 머지 커밋과 같은지 본다. **새 배포는 뜨자마자 수집·경보 주기를 한 번 돈다** — 다음 정시를 기다리지 않아도 첫 관측이 나온다.

## ★ 로그는 배포 단위로 쪼개진다 ★

배포가 있었던 날 `serviceId` 로만 조회하면 이전 배포의 사이클이 통째로 안 보여 **없는 결손을 보고하게 된다.**
반드시 **deploymentId 별로** 조회한다. 다만 배포 자체가 사이클을 죽일 수도 있으니(2026-08-22)
'배포 때문에 안 보임'과 '안 돌았음'을 구분해 적는다(`list-deployments` 시각 ↔ uvicorn 기동 줄 대조).

## 로그 줄 용어집

| 줄 | 뜻 | 슬롯 |
|---|---|---|
| `📊 소스 건강: 정상 N/M · …` | `중단`·`값없음`·`늙는중` 이 붙으면 문제 소스. **M 은 늘어난다 — 로그의 숫자를 믿는다** | 수집 주기 |
| `🚨 경보 주기: 등급별 건수 · 내림 N건 · 알림: … \| 이름(근거)…` | 알림 상태와 상위 3개 경보 | 매시간 :01 전후 |
| `🔇 부정적 공간: 판정 N개 · 급감 N건 / 제외 …` | 판정한 지표 수와 걸러낸 사유 | 매시간 |
| `🧮 [alerts] 소표본 유의도 social_X: 관측값 N · 과거 평균 M · kσ (문턱 2.0σ) → 통과/경보로 안 올림` | `social_*` 의 승격 직전 계산값. **통과·차단 모두 찍힌다** — 실제 과거 평균이 값으로 읽힌다 | 매시간(해당 지표가 후보 문턱을 넘은 주기) |
| `🔽 내림: 등급 이름 점수 [source] · …` | 오늘 화면에서 내려가 있는 행 전부 | 매시간(있을 때) |
| `🌐 무역 스캔: 새로 조회/캐시 N분 전 · 품목 a/b달[429 재시도 n회][500행 상한 k달] → N개국 · … · 부분 스캔 k/3 · 캐시 저장` | 무역 경보(`trade_surge`)의 입력. **부분 스캔**은 일부 품목 조회가 비었다는 뜻 — 그 결과가 6시간 캐시될 수 있다 | 매시간 |
| `🧢 [alerts] social_X — 이상도 N점을 경보 점수 79.0점으로 제한` | 단독 사회 카운트 신호의 경보 점수 상한이 걸렸다 | 해당 지표가 후보일 때 |
| `🚨 경보 주기: … · 알림: 전송 실패(미전송 N건, 다음 주기에 재시도)` | 텔레그램 전송이 실패해 기록하지 않았다. 다음 주기에 다시 시도한다 — 연속으로 찍히면 채널 문제다 | 전송이 실패한 주기 |
| `⏸ 판정 안 함: … — 이번 주기 스캔이 불완전해 내리지 않고 마지막 상태 그대로 둠` | 무역 스캔 실패로 **내림이 아니라** 보류한 행. `🔽 내림` 과 다른 사실이다 | 스캔이 불완전한 주기 |
| `기준 스냅샷 X: 없어서 새로 받음 / ⚠ … 없어서 받아 봤으나 <사유>` | 파일이 없는 기준 스냅샷을 주간 타이머와 무관하게 6시간에 한 번 받아 본 결과 | 파일이 없는 동안 6시간마다 |
| `📌 정답 적재 N건 / 검토 N건 · 선언아님 · 신뢰도미달` | 공식 선언을 정답 테이블에 올린 결과 | 21:00 UTC 슬롯 |
| `📋 예측 기록: N개국 …` + `- 나라: 위험도 N점 · 질병 · 신뢰도` | 새 예측(질병 이름 또는 `질병 미지목`). **정기 보정 기록**(경보 아님)도 같은 줄로 찍힌다 | **매 시간**(새 기록이 있는 주기에만 `📋`) |
| `해소할 예측 없음(미결 N건)` | 채점기 결과 | 21시대 |

알림 필터: `알림: 전송됨` 이 폰이 울린 것이다. **필터 결과가 비면 0건이다**(못 본 것과 구분해서 적는다).

## 검증 절차 (머지 뒤)

1. `list-deployments` → 새 배포 id·`commitHash` 확인.
2. 그 deploymentId 로 **수정이 낸 줄**을 `filter` 로 찾는다.
3. 찍혔으면 그 값이 *정당한가*를 같은 사이클의 다른 줄과 대조해 판정한다(예: 내려간 행 ↔ 같은 시각 수집 값).
4. 안 찍혔으면 **'안 찍힘'인지 '못 봄'인지 갈라 적는다.** 슬롯이 아직 안 왔으면 '판정 보류 + 볼 시각'.
5. 자정에 사라지는 상태는 **당일 안에** 본다.

## 못 봤을 때

Railway MCP 가 죽으면(스키마 오류 등) 재시도 후에도 안 되면 **'못 봄'** 으로 적고 **무엇을 못 봤는지 항목으로 나열한다.**
도구가 돌아오면 소급 관측한다. 못 본 날을 '이상 없음'으로 적지 않는다(09-23 에 그렇게 하지 않았다).
매일 점검 전체 절차는 `docs/매일_수집점검_절차.md`.
