## 1. 헤드라인 — 11-06 02:00 UTC 수집 주기 하나가 **통째로 빠졌다**

24시간 동안 정시 수집은 **23/24회**다. 빠진 시각은 **02:00 UTC**.

"늦게 왔다"가 아니라 **건너뛴 것**이고, 로그가 이유를 직접 말한다:

```
[01:45:57] === 무료 소스 수집 시작 ===     ← 구 컨테이너가 수집 시작
01:47:50   Killed                          ← 배포가 컨테이너를 죽임
[01:47:49] ⏭ 무료 수집 건너뜀 — 다른 프로세스가 실행 중
[01:59:59] ⏭ 무료 수집 건너뜀 — 다른 프로세스가 실행 중   ← 02:00 주기 손실
[03:00:00] === 무료 소스 수집 시작 ===     ← 65분 뒤 락이 삭아서 재개
```

### 왜 — 기전이 특정된다 (추정 아님, 코드에 그대로 있다)

- `main.py:838` / `:858` → `_watched("무료 수집", …, job="free-collect", timeout=3300)`
- `main.py:390` 근처 `_watched` → `job_lock.acquire(job, int(timeout) + 600)` ⇒ stale 문턱 **3900초 = 65분**
- `algorithms/job_lock.py` — 락은 `data/locks/free-collect.lock` **파일**이고 그 경로는 **Railway 볼륨**이다 → 컨테이너가 죽어도 파일이 남는다
- `job_lock.release()` 는 `owner_pid == os.getpid()` 일 때만 지운다. `Killed`(SIGKILL) 에는 release 가 돌 기회가 없고, **새 컨테이너는 pid 가 달라 남의 락을 지울 수 없다**
- 그래서 `_break_if_stale()` 이 **65분**을 기다려야 깨진다. 01:45:57 + 3900s = **02:50:57** → 02:00 주기는 그 안에 들어가 죽고, 03:00 이 첫 복귀다

### 오늘만의 일이 아니다 — 5일에 4번, 전부 배포 직후

| 날짜 | 잃은 정시 주기 |
|---|---|
| 11-02 | **16:00**, **18:00** UTC (2회) |
| 11-03 | **16:00** UTC (1회) |
| 11-06 | **02:00** UTC (1회) |

사고 ②(2026-08-22, 배포가 틱을 죽여 그날 통째로 빠진 건)와 **같은 계열**이다.
그때 넣은 따라잡기 수집은 작동하고 있지만(01:26·01:45 에 추가 수집이 돌았다),
**락이 따라잡기보다 오래 살아서** 정시 주기를 먹는다.

### 고칠 지점 (코드는 안 건드렸다 — 캡틴 결정)

1. **(권장·가장 작다)** 기동 시 락 청소. 컨테이너는 pid 네임스페이스가 새로 생기므로
   **기동 순간에 존재하는 락 파일은 정의상 전부 잔해다.** `job_lock.py` 에
   `clear_stale_on_boot()` 를 만들고 `main.py` 기동 훅에서 한 번 부른다.
   (`job_lock.py` docstring 이 이미 "단일 인스턴스 전제"를 못박아 뒀으니 이 가정이 안전하다.)
2. 대안: `_break_if_stale()` 에서 `os.kill(owner_pid, 0)` 로 주인 생존을 확인해 죽었으면 즉시 뺏는다.
3. 대안: 작업 중 주기적으로 락 파일 mtime 을 갱신(heartbeat)하고 `stale_sec` 을 65분에서 크게 줄인다.

**곁가지 결함**: 락에 막혀 건너뛸 때 이미 만들어둔 코루틴을 await 하지 않아
`RuntimeWarning: coroutine '_run_collector' was never awaited` 가 매번 찍힌다
(`main.py:838`·`:858`). 기능엔 영향 없지만 코루틴을 늦게 만들거나 `close()` 하면 사라진다.

## 4. 브리핑 — 확인 못 했다. '정상'이라고 쓰지 않는다

- 브리핑은 `main.py:619` `_DAILY_BRIEF_HOUR_UTC = 22` 라 **22:00 UTC 주기에 생성**된다. 지금은 23:13 UTC 이므로 시각은 지났다.
- 22:00 UTC 주기는 정상적으로 돌았다(`[21:59:59] === 무료 소스 수집 시작 ===`, 22:02 경보 주기 정상).
- `daily_brief_job failed(...)` · `브리핑을 한 언어도 생성하지 못함` · `텔레그램 발송 실패` — **이 실패 줄들이 하나도 없다.**
- ⚠️ **그런데 이것은 성공의 증거가 아니다.** `_run_daily_brief_job()` 은 **성공 시 로그를 한 줄도 남기지 않고**,
  09-18 절이 밝혀낸 대로 `daily_brief.py:840` 의 `except Exception: return None` 때문에
  LLM 이 죽어도 조용히 `generation_method: "template_fallback"` 으로 떨어진 채 **정상 반환**한다.
  → **"에러가 없다"와 "LLM 으로 만들어졌다"는 다른 말이다.** 아카이브 3개 언어(ko·en·fr) 유무도, `generation_method` 도
  `/api/daily-brief/archive` 가 403 에 막혀 **못 봤다.**
- 확인법(브라우저): `…/api/daily-brief?lang=ko&format=duo` 를 열어 `generation_method` 를 읽는다
  (포맷을 명시해야 캐시를 비켜간다 — `main.py:1790`). `fr` 아카이브가 비어 있으면 08-23 회귀다.
