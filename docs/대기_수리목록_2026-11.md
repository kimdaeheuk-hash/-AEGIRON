## ⑥ ✅ 수리함(2026-11-16) · PolarWatch 14시간 중단 — 요약 줄이 수집한 자료를 버렸다

- **관측**: 11-14 21~23시(3주기) → 00:03 자동 복구 → **11-15 10시~23시 14주기 연속 `중단`**.
  에러는 한 종류뿐: `TypeError: must be real number, not NoneType`.
- **원인**: `collector.py` 극지 요약 줄의 `%.0f` 가 `polar_watch_score=None` 을 만났다.
  바로 윗줄 `sorted(... or 0)` 은 같은 None 을 막고 있었다 — **경계에서 자격이 떨어져 나간 모양**
  (`boundary-audit` 계열). None 은 고장이 아니라 설계다(`compute_region` 이 "모른다"로 돌려준다).
- **피해**: `except` 가 `result["polar_watch"] = None` 으로 덮어써서 **이미 받아온 8개 관측지
  자료를 매 주기 버렸다.** `record_cycle` 이 None 을 수집 실패로 세어 소스까지 죽었다.
- **새 회귀 아님**: 같은 코드가 11-15 00~09시 정상. 마지막 배포(06:12)는 2차 발생(10:00)보다 앞.
  방아쇠는 외부 자료, 결함은 우리 것(잠복).
- **고친 것**: 수집만 `try`, 요약은 `else` + 제 몫의 `try`. 요약 실패에는 `log_error` 를 안 부른다.
  점수 None 표기와 모르는 관측지 세기는 **#124(같은 날, 다른 세션)의 것을 썼다** —
  `점수 없음` + `기상 자료 없음 N/M(판정 안 함)`. 8곳 **모두** 기상 자료가 없으면 수집
  실패로 세는 판정도 #124 쪽이 더 낫다. 이 PR 이 남긴 몫은 **구조**다: 판정을
  `polar_weather_ok` 로 떼어내 서식보다 **먼저** 하고, 찍는 일은 제 몫의 try 에 둔다.
  #124 는 `%.0f` 하나를 고쳤고, 서식이 다음에 다른 이유로 터지면 같은 손실이 되풀이된다.
- **드러난 것**: 같은 입력에서 **8곳 중 7곳이 기상 자료 없음**이었다. TypeError 가 그걸 가리고 있었다.
- **다음 점검**: `기상 자료 없음 N/M` 의 N 을 적어라. 계속 5~7이면 수집은 살았어도 이 층은 눈을 감은
  것이고, 수리 대상이 Open-Meteo(해빙)/극지 뉴스 피드 쪽으로 옮겨간다.

## ⑪ (11-16 추가) `MIN_PUBLISHERS=2` 문턱 — 근거가 쌓이면 결정

깔때기(업그레이드 ③)가 `매체부족` 을 세기 시작했다. 병원체 보도가 **왔는데** 매체가
한 곳이라 못 올린 경우다. 이 층이 노리는 게 '사건 하나가 곧 뉴스' 인 병원체이니
문턱 2가 맞는지는 실측으로 답할 질문이다.

- **지금 할 일**: 며칠 동안 `매체부족 N ⟨예시⟩` 를 모은다. 예시가 진짜 사건처럼
  보이면 문턱을 1로 낮추는 안을 캡틴에게 올린다.
- **문턱은 안 건드렸다** — 1로 낮추면 한 매체의 오보 하나가 바로 화면에 오른다.
  이건 측정이 아니라 정책이라 실측 없이는 못 정한다.
